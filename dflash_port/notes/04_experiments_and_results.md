## 0. Ground rules the author applied (affects how much to trust anything below)

- Every serving result is a SINGLE run, single seed (42), 50 prompts/category, C1 unless stated, 256 max output tokens, 3 draft tokens, 3 warmups, `correctness_status: not_checked`. No repeat variance exists anywhere. (`RES/README.md`, `RES/GEN-011..013`.)
- GEN-002 (`RES/GEN-002-http-token-equality.md`): target-only greedy output was NOT reproducible (23/50 exact matches vs its own repeat; EAGLE3 repeat 50/50; target-vs-EAGLE3 17/50). Author deferred this and runs timing with `--allow-output-mismatch`. So no speedup is "verified lossless".
- Most training ablations (GEN-001, 004, 005, 006, 007, 009) are W&B screenshots only: "visual readings, not exported measurements", one seed. Raw exports never supplied.
- "Throughput" = aggregate output tok/s = output tokens / measured wall seconds including prefill and serving overhead (not GuideLLM per-request median). Generator generate+merge+restore time (about 6.5 ms/request, 0.15-0.24% of wall) is INCLUDED in wall time, i.e. generator latency is NOT netted out; it is just negligible at C1 with one adapter per request.
- No target-only (no speculation) throughput baseline exists in any record. All "speedups" are vs the base EAGLE-3 drafter (or vs static LoRA), never vs vanilla Qwen3-8B decoding (`RES/GEN-003...md:91`; `BM/2026-10-21-nemoall50/README.md`: "ratios measure additional benefit over EAGLE3, not speedup over target-only").
- Cross-run comparisons (historical rows vs new) are explicitly "descriptive, not controlled": runtime/hardware/precision (FP32 historical vs BF16+batched new) differ. The paired DeepSeek baseline reran 4.9% faster than its earlier standalone run with identical acceptance (82.50 -> 86.58 math), a direct measure of run-to-run/environment drift of about 5% (`RES/GEN-012:` "Use the paired baseline"). Treat any throughput gap under about 5% as noise.

### 2.4 End-to-end vLLM speedup, concurrency, latency accounting

- Concurrency: C1 is the headline setting. Shared-adapter fixed-cohort C1/2/4/8 (`BATCH-001`): G4 vs EAGLE3 ID mean +13.73/+14.65/+14.89/+13.08%; OOD mean +1.66/+1.79/-0.82/+0.20%. At C8 math G4 vs EAGLE3 +21.9%, HumanEval -4.68%. Absolute C8 G4 math 451.59 tok/s vs EAGLE3 370.40.
- Per-request adapters, native continuous batching, C4 (`BATCH-003`): math +9.33%, code -0.70%, STEM -0.82%, chat -4.76% vs native EAGLE3 (C1: +6.42/+1.26/+0.59/-7.25; C2: +5.45/-2.09/-1.22/-9.19) despite acceptance length +22.2/+14.1/+13.1/+5.9% at C4. TTFT +10..+18 ms. C8 absent.
- Profiling (`SYS-002`): C1 math 60.91 (vanilla) / 78.32 (merged gen) / 65.20 (multi-LoRA) tok/s; multi-LoRA is 16.75% slower than merged on math, 14.64% on chat at the same acceptance. Cause per trace: per-call LoRA metadata mapping on CPU (sort, unique, 1,032 scalar syncs vs 62, +2,468 CUDA launches); LoRA GEMM kernels are only 3.6-6.8 ms total. Unmerged per-request LoRA in vLLM is the throughput killer, not the matmuls.
- Latency netting: generator time was NOT subtracted; it is part of wall time and is small (3.1 ms generate + 3.2 ms merge + 0.26 ms restore per request at C1; all-module 5.7+9.7+0.7 ms; decoder-256 2.6+3.2+0.27 ms). In the shared-adapter C8 case it is 0.07-0.11% of wall. The author repeatedly states that these CUDA-event timings "do not explain" the throughput-vs-acceptance gaps; no isolated drafter/verifier timing exists.
- Cost: the closed-cohort shared adapter inflates TTFT enormously with concurrency (G4 chat median TTFT 49.6 ms at C1 -> 1,447.6 ms at C8). Author's verdict: "limited practical usefulness of the current fixed-cohort, shared-generator-adapter batching technique" (`BATCH-001` update 10-25). Hence the DFlash port should target the C1 / merged-per-request regime or an efficient batched-LoRA kernel, not shared cohorts.
- Best claim supportable: at C1, merged-per-prompt generator gives +3% to +29% tok/s over base EAGLE-3 depending on category and drafter strength (Red Hat drafter: up to +28.7% math; DeepSeek drafter: +6.6..+16.1% ID, +1.3..+5.3% OOD), all vs base EAGLE-3 not vs target-only.

## 4. Methodology notes, audits, bugs, caveats, open questions

Seeds / sizes / eval sets
- Training seed 42 everywhere; ablation pairing uses identical seed-42 episode schedule. Serving seed 42.
- Offline validation: ctx-4 cohorts, 100 val rows/domain from shard 00000 (400 total) every 250 updates (GEN-001, structure v1); v4 study splits held shard 00000 into 50 tuning / 50 test per category; 100K run uses 1,000 val rows (250/cat, 10 per subset), 24K run 400 rows. Offline metrics are teacher-forced agreement/loss, NOT acceptance.
- Serving eval: Nemotron ID subsets (e.g. chat-00000, 00002..00005; hashes archived) and Red Hat `speculator_benchmarks` OOD (HumanEval raw prompts, math reasoning, summarization). Note: OOD formatting differs per category ("category and formatting shifts are confounded"). Validation subset 00000 is also represented in training pools for GEN-001 (leak-by-identity, not by row).
- Chat OOD distribution: no mixed-domain serving was ever tested (cohorts are same-category).

Training audit "Audit actual 24K versus 100K training exposure" (`BM/2026-11-01-attention-100k-2k-c1/training_audit/{README.md,audit.json,24k,100k}`, GEN-013 follow-up), commit 0aa0272:

## 6. Lessons for the DFlash port

Default starting recipe (what demonstrably worked, in order of confidence)
1. Frozen drafter + hypernetwork that emits LoRA on ALL attention projections (Q/K/V/O), rank 32, alpha 64, dropout 0.05, scale fixed at training value (alpha/r = 2 here). Do not raise inference scale (s=8 collapses; 4 is worse than 0.5/2).
2. Generator: encoder 512 -> example 128 -> condition 64, descriptor 32, decoder 256 (compact, same acceptance, -17% latency, -49% params), 2 residual blocks (1 is enough), BF16 params/optimizer + batched cohorts (gradients flow through functional param substitution; accumulate microbatch factor grads then one generator backward).
3. Conditioning: `last` prompt token's target hidden states (layers 2/18/33 concat) with cohort mean/std/count pooling; for serving use K=1 (single prompt, per-request, merged) - larger K showed no benefit. Singleton conditioning at train time must match serving; the author trained cohorts 1-8 but serves K=1.
4. Loss: `lk_hybrid` (KL/TV adaptive blend, eta=3) at all TTT steps; LK about equal CE offline, replay/on-policy objectives hurt. For DFlash (block diffusion drafting) the analogue is the drafter's own training loss on teacher-forced saved target responses (regenerated by the target; thinking off). Keep it off-policy/saved-trajectory.
5. Optimization: AdamW lr 1e-4, wd 0.01, clip 0.85 (log pre-clip norm), 100-update linear warmup then constant, token-budget microbatches 8,192, 4 cohorts/update, seed 42, validation every 250 updates, 1,500 updates pilot (4K examples, 1K/domain) -> 2,000 updates on 24K. Expect most gain in first 250 updates; 4K vs 16K pool indistinguishable at 1,500 updates.
6. Serving: merge the per-prompt adapter into the draft weights once per request (generate 3 ms + merge 3 ms + restore 0.3 ms), measure at C1 with 3 (or block size) draft tokens. Avoid vLLM native multi-LoRA for the draft path unless the metadata-mapping/sync overhead is fixed (it costs 15-17% throughput). Do not use fixed-cohort shared adapters (TTFT blows up at C8).

Ablations worth repeating for DFlash (cheap, high information)
- Matched static LoRA with the same target modules/data/updates (the decisive control; author's best matched evidence shows math +4-6 pp acceptance but chat none).
- Conditioning controls: correct vs same-category donor vs cross-category vs fixed donor (same-category never run in the fork).
- Module set: attention vs attention+MLP (all-module won offline, lost on cost/throughput).
- Frozen-drafter strength: the generator helped the stronger DeepSeek drafter more ID, less OOD; DFlash drafters are strong, so measure paired baseline in the same suite/session.
- Repeats: 3 interleaved runs per cell. Run-to-run drift of about 5% was observed; every gap under 5% in this fork should be considered unresolved.
- Add a target-only baseline for a real end-to-end speedup, and per-position acceptance (DFlash: per-block-position acceptance) plus accepted length.
- Evaluate on both ID and OOD (HumanEval/math-reasoning/summarization); OOD gains are small (+1..+6%).

Dead ends / not worth repeating
- LoRA-bank warmup (retired; fresh generator catches up).
- On-policy replay / verified-prefix refresh / acceptance feedback (replay -2.6 pp, feedback no gain on saved-response continuation).
- Fixed LoRA scale > training scale, or scale tuning generally (s=2 best).
- Bigger hypernet trunk (decoder 1024, deeper blocks, condition_dim 128): no gain; encoder_hidden 1024 only a weak signal.
- All-module generation as a default (best math acceptance 67.79% but slower, 16 ms/request adapter cost).
- Shared-adapter cohort batching for deployment; K>1 conditioning.
- Pool 4K->16K at fixed updates, and 24K->100K at 2K updates (no gain; 100K was slower). If scaling data, give the pool enough updates (about 8.3K+ for equal reuse); the 10K-update TTT7 run was launched but has no recorded result.
- Rank 8->64: monotone but small (+1.8 pp from 8 to 64), undocumented config.

Practical expectations for DFlash: realistic target is +5..+15% C1 tok/s over base drafter ID, +1..+5% OOD, with acceptance gains of 4-13 pp; chat/open-ended text gains smallest; the stronger the base drafter, the larger the ID gain.

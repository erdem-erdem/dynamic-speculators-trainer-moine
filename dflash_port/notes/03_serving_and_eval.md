## 1. Serving architecture and the vLLM patch

### 1.1 What is patched, and how
- Pinned to **vLLM 0.31.0**, commit `db9527a46873454610df6dbedf79a36d6bf1a7f6` (`S/bundle.py:18-19`, `S/patches/manifest.json:2-3`). Hard version gates: `S/controller.py:513-514` (`initialize_proposer`), `S/server.py:68-71`, `S/worker.py:81-84`, `S/patch.py:144-145`. `scripts/evaluate/requirements.txt` pins `vllm==0.31.0`, `guidellm==0.7.1`. `pyproject.toml:40` lists plain `"vllm"` (unpinned).
- Mechanism: **source patch applied in place to the installed vLLM package** (Python only, no rebuild). `scripts/apply_vllm_generator_patch.py --check|--apply|--revert` -> `S/patch.py:patch_sources`. Uses exact-string anchor replacement (`manifest.json` `replacements`), SHA256 before/after per file (`patch.py:152-168`), backup dir `<root>/.speculators-generator-vllm-0.31.0` (`patch.py:13,169`), transactional write with rollback (`patch.py:203-224`). Human-readable diff is `S/patches/vllm-0.31.0-generator.patch`.
- Three vLLM files are modified:
  1. `vllm/config/speculative.py`: adds `SpeculativeConfig.draft_adapter_path: str | None` (patch lines 45-55, manifest 9-13).
  2. `vllm/v1/spec_decode/eagle.py`: the **EagleProposer** class (the anchor is the tail of its `__init__`, `runner=runner,\n        )`) gets: `__init__` tail -> `initialize_proposer(self, runner)` (validates runtime); `load_model` override -> `self.draft_adapter = create_controller(self)` after `super().load_model`; `propose` override -> `prepare_proposer(self, kwargs["target_positions"], kwargs["target_hidden_states"], kwargs.get("common_attn_metadata"), proposal_kwargs=kwargs)` **before** `super().propose`; `build_per_group_and_layer_attn_metadata` override -> `draft_adapter.map_forward(common_attn_metadata)` (continuous mode only); `dummy_run` override (memory profiling, runs generator/merge or native LoRA kernels); `on_requests_finished` (patch lines 56-105).
  3. `vllm/v1/worker/gpu_model_runner.py`: at top of the finished-request cleanup in `_update_states`, calls `drafter.on_requests_finished(scheduler_output.finished_req_ids)` (patch 106-118).
- Also uses vLLM extension points, not patches: `--worker-extension-cls speculators.generator.serving.http.AdapterWorkerExtension` (`S/server.py:23,~262`), `--middleware speculators.generator.serving.http.AdapterMiddleware` (`S/http.py:78`), optional `--scheduler-cls speculators.generator.serving.scheduler.FixedBatchScheduler` (`S/scheduler.py`, `S/cohort.py`).

### 1.2 Request flow (server, HTTP path)
1. Client -> `/v1/completions` (matched workload uses completions with raw token-id prompts, no chat template re-applied; `S/guidellm.py:300-350`). `AdapterMiddleware` assigns a fresh `X-Request-Id` uuid so response id `cmpl-<uuid>` can be mapped to the internal id (`S/http.py:107-123`), and on completion/disconnect calls RPC `speculators_finish_http_request` (`http.py:128-146,164-171`).
2. vLLM scheduler: unchunked full target prefill (must be complete; chunked prefill disabled).
3. Target prefill runs normally and the EAGLE-3 aux hidden states are captured by vLLM's own mechanism. After target prefill/verify, vLLM calls `EagleProposer.propose(..., target_positions=, target_hidden_states=, common_attn_metadata=...)`. The patched `propose` calls `prepare_proposer` (`S/controller.py:520-562`).
4. **Source of conditioning hidden states at serve time**: the `target_hidden_states` argument of `propose()` on the first proposal for a request == the aux (concatenated multi-layer) target states for all prompt tokens. Generator input = **the last prompt token's row only** (`states[-1:]` serial `controller.py:322`; `states[end-1:end]` per-request `per_request.py:319`; per-row stacked for fixed batches `controller.py:393-410`), cast to float, plus the prompt length. Enforced: positions must equal `arange(prompt_length)` ("complete target prefill", `controller.py:308-319`, `per_request.py:315-318`). Only `condition == "last"` is supported (`bundle.py:51-52,127-128`). Width check `summary.shape[1] == metadata["input_dim"]` (`controller.py:323,413`; `per_request.py:282`).
   - Hidden-state layer ids: `bundle.json["layer_ids"] = manifest.cache_spec.hidden_states.layer_ids[:-1]` (`bundle.py:167`) (last id is the verifier final state used for training loss). Doc: Qwen3-8B/RedHat drafter uses raw target states at layers `[2, 18, 33]` concatenated (input_dim 12288). `validate_runtime` **overwrites** `spec.draft_model_config.hf_config.eagle_aux_hidden_state_layer_ids = metadata["layer_ids"]` (`controller.py:135`), so vLLM captures exactly those layers. For the DeepSeek `eagle3_qwen3_8b_ttt7` drafter: layers `[1,9,17,25,33]` zero-based -> vLLM ids `[2,10,18,26,34]`, input_dim 20480 (`B/deepspec.py:278-305`, `examples/eagle3-lora/deepseek_ttt7_generator_v1/README.md`).
5. Generator runs (`self.generator(summary, torch.tensor([length]))`) -> factors {proj: (A [r,in], B [out,r])} (rank 32, alpha 64).
6. Adapter is applied (merged or per-request native LoRA, see 2), then vLLM runs draft prefill/draft steps with the adapted drafter, target verifies as usual (unchanged accept/reject).
7. Request end: adapter released/weights restored via lifecycle hook + HTTP middleware RPC.
- Adapter is **fixed for the whole request** (no refresh) in production modes. `S/experiments.py` (`ExperimentalAdapterController`, C=1 merged only) implements research variants: refresh from prefix, feedback-conditioned, donor-conditioning controls (`conditioning: correct|fixed|same_category|cross_category`), prefix hidden states via `states[end-1:end]` after trimming `num_rejected_tokens_gpu` (`experiments.py:84-113`).

## 2. Shared merged serving vs per-request native LoRA

### 2.1 Shared merged path (`DraftAdapterController`, `S/controller.py:251-467`)
- Supports every module in `ADAPTER_MODULES = up_proj, down_proj, gate_proj, q_proj, k_proj, v_proj, o_proj` (`generator/config.py:13-21`; `controller.py:47,147-158`). The DeepSeek generator is Q/K/V/O, served this way (concurrency 1 shared; `benchmarks/math_chat_c1.yaml`).
- Merge: `AdapterMerger` writes `W_base + (alpha/rank) * B@A` (fp32 math, cast to bf16) **in place into vLLM's packed weights** (qkv_proj sliced Q/K/V rows, gate_up_proj sliced halves, o_proj, down_proj; `controller.py:138-248`); base copies kept (`self.base`) and restored by `copy_` (not subtraction; `controller.py:196-200`). Requires exactly **one draft layer** (`controller.py:143-144`), TP=1.
- Static LoRA bundle: `static_adapter_policy == "merged_once"` merged once at startup (`controller.py:270-278`), never restored.
- Batching across requests: **cannot** hold different adapters (single weight tensor). Policy `fixed_shared_adapter`: `FixedBatchScheduler` (`S/cohort.py`) forms **closed cohorts** (<= max_num_seqs, waits `batch_wait_ms`=50 ms at an idle boundary; no refill until all members finish; KV preemption raises). `prepare_batch` pools the cohort's last-token summaries (optionally a seeded subset of size `conditioning_examples` K, `controller.py:402-411`) into **one** generator call -> one adapter shared by all members (generator conditioning pooling over contexts 1-8). Max cohort/concurrency 8 (`MAX_BATCH_SIZE`, `server.py:22`).
- Generator invoked once per batch; merge once per batch; restore after the last member (`controller.py:449-467`). Counted: `generator_seconds`, `merge_seconds`, `restore_seconds`, `adapter_load_seconds` in `totals`, exposed at `/speculators/status` (`http.py:16-50`).

### 2.2 Per-request native LoRA hook (`PerRequestAdapterController`, `S/per_request.py`; `NativeDraftLoRA`, `S/multilora.py`)
- Activation: `--adapter-policy per_request --batching-policy continuous` (+ `conditioning_examples` must be 1) (`server.py:105-115`), `SPECULATORS_SERVER_CONFIG["adapter_policy"]=="per_request"` -> `create_controller` (`per_request.py:424-447`).
- **Claim verified: only o_proj/v_proj.** `controller.py:57-62`: `continuous and set(metadata["shapes"]) != {"o_proj","v_proj"}` -> `ValueError("Per-request adapters support only o_proj/v_proj; use shared merged serving for other projections")` (exact set equality, so Q/K or MLP generators are rejected; a bundle with only one of the two is also rejected). `multilora.py:468-474` hard-codes `target_modules=["v_proj","o_proj"]` and asserts the vLLM LoRA manager wraps exactly `{model.layers.0.self_attn.qkv_proj, model.layers.0.self_attn.o_proj}` (`multilora.py:484-491`); adapter path `model.layers.0.self_attn.{name}` (`multilora.py:511`). Hard-wired to `draft.model.layers[0]`, i.e. one draft layer.
- Mechanism: uses vLLM's own `create_lora_manager` (`vllm.lora.model_manager`) on the **draft model only** with a separate `LoRAConfig(max_lora_rank=rank, max_loras=max_num_seqs, max_cpu_loras=max_num_seqs, lora_dtype=bf16)`; target stays LoRA-free (`controller.py:111-112` requires `config.lora_config is None`). Each new request -> `LoRAModel(adapter_id, rank, layers)` -> `manager.add_adapter` + `activate_adapter` (slot upload), mapping by `LoRAMapping(tuple(token_ids), tuple(request_ids), is_prefill=True)` (`multilora.py:494-538`).
- Cross-request batching: standard vLLM scheduler (continuous admission), different adapters per token through vLLM's multi-LoRA (punica) kernels. `map_forward` (patched `build_per_group_and_layer_attn_metadata`) rebuilds the token->adapter map from `query_start_loc_cpu` for **every draft forward** (including later speculative steps) (`per_request.py:364-379`). New requests get a generator call in `prepare_scheduled` (only for ids not in `self.adapters`; adapters cached on CPU as bf16 copies, GPU slots only for scheduled requests; `per_request.py:292-362`, `multilora.py:495-528`). Capacity = max_num_seqs (<= 8).
- Caveat in docs: unmerged bf16 LoRA branch rounds differently from merged bf16 weights; "CPU tests only; native CUDA kernels and full A100 serving run have not been executed in the development environment" (`docs/experiments/eagle3_per_request_lora.md`) - check results docs for whether this was later run.

### 2.3 Generator latency handling
- Generator runs **inside the engine step** on the GPU, synchronous, between target prefill and draft prefill, timed with CUDA events + `end.synchronize()` (`controller.py:28-42` `elapsed`). Per-request mode additionally copies factors to CPU (`per_request.py:288-289`) and uploads to slots (adapter_load_seconds).
- It is **included in wall-clock** request latency/TTFT/throughput in all harnesses (HTTP: GuideLLM measures client-side; offline: `request_seconds` around `generate`, `S/worker.py:131-139`). Docs: "Server-side generator and merge overhead remains inside measured request latency". It is also recorded separately (`generator_seconds`, `generator_ms_per_call`, `endpoint.py:149-151`) but **never subtracted** from speedups.
- Warmups are excluded from acceptance/adapter counters (counter snapshots after warmup, `guidellm.py:301-318`).

## 3. Bundle format (`S/bundle.py`)
- Directory: `bundle.json` + `model.safetensors` (+ copied provenance files listed in `PROVENANCE`, `bundle.py:21-40`: resolved_experiment.json, train_command.txt, speculators.patch, result.json, metrics.json, timing.json, configuration.json, wandb.json, eval_command.txt, provenance/, study.json, validation.json, ...). The task description's "configuration.json" is just one copied provenance file; the actual bundle manifest is `bundle.json`.
- `bundle.json` keys (written `bundle.py:162-190`): `version`=1 (`BUNDLE_VERSION`), `kind` in {`generator`,`static_lora`}, `models` = {target:{id,revision}, drafter:{id,revision}} (full 40-hex SHAs required at serve time, `server.py:27`), `condition` ("last" for generators else null), `layer_ids` (aux layer ids), `rank`, `alpha`, `shapes` {proj: [in_features, out_features]}, `source_identity` (digest of resolved_experiment), `source_job`, `source_checkpoint_sha256`, `draft_config` (frozen drafter config.json), `weights_sha256`; generators add `feedback_dim`, `input_dim` (= encoder.0.weight.shape[1]-1), `architecture` (generator Architecture), `max_examples`, optional `training_conditioning_examples`.
- Weights: generator -> full generator `state["model"]` (keys like `encoder.0.weight`, `heads.<proj>.A.bias`, `heads.<proj>.B.bias`), bf16 preserved, finite check (`bundle.py:198-201`); static LoRA -> `{proj}.A`, `{proj}.B`.
- Export: `export_run` (`bundle.py:75-221`) reads `checkpoint.pt` (mmap, weights_only), checks `identity` digest vs `resolved_experiment.json`, atomic `.pending` rename. Refuses quantized drafter (`:119-120`).
- Load: `read_bundle(path)` validates version/kind/`condition=="last"`/shapes subset of `ADAPTER_MODULES`/weights sha256 (`bundle.py:43-57`); `bundle_state(path)` = `(read_bundle, load_file(model.safetensors, device="cpu"))` (`bundle.py:224-226`); `load_generator(metadata, state)` rebuilds `LoRAGenerator(input_dim, shapes, rank, Architecture, max_examples, feedback_dim)` and `load_state_dict(strict=True)`, eval, no grad (`bundle.py:60-72`).
- `validate_runtime` also checks: bundle's target/drafter id+revision pin match served models (`controller.py:117-128`), frozen drafter normalization flags (`norm_before_residual`, `norm_before_fc`, `fc_norm`, `norm_output`) match `draft_config` (`:129-134`), and overrides aux layer ids (`:135`).

## 4. Evaluation metrics, workloads, comparisons

### 4.1 Two online harnesses
A. **HTTP + GuideLLM (the current campaign path)**: `speculators benchmark suite --config <yaml> --output-root <dir> [--resume] [--dry-run] [--ttt N]` (`src/speculators/cli/benchmark.py`, `B/suite.py`) launches `scripts/launch_vllm.py serve ...` per (model x concurrency), waits ready (`B/processes.py:wait_ready`), then runs `scripts/evaluate/evaluate.py throughput --validation-manifest ...` -> `S/guidellm.py:benchmark_endpoint` (guidellm==0.7.1 hard check `guidellm.py:184`). `speculators benchmark profile` for torch-profiler traces (`B/profiling.py`, `B/trace.py`).
B. **Serial offline-LLM harness** (historical): `speculators generator benchmark --config examples/eagle3-lora/vllm_math.yaml [--smoke]` (`S/benchmark.py`, `S/worker.py`): one fresh process per arm {target_only, eagle3_base, fresh_lora, transferred_lora, fresh_generator, pretrained_generator}, `vllm.LLM(...)`, max_num_seqs=1, 100 prompts `math-00001`, 3 warmups, 3 repetitions, greedy, seed 42.

### 4.2 Metric definitions
- Acceptance (online): vLLM Prometheus counters `vllm:spec_decode_num_drafts`, `..._num_draft_tokens`, `..._num_accepted_tokens`, `..._accepted_tokens_per_pos`, differenced before/after each category (`scripts/evaluate/perf_utils.py:326-348`, `guidellm.py:316-372`). `acceptance_length = 1 + accepted/drafts` (`perf_utils.py:344`); `acceptance_at_pos_i = count_i/drafts`; also `draft_acceptance_rate = accepted/draft_tokens`, `accepted_prefix_length = accepted/drafts` (`guidellm.py:366-372`). Offline harness: same formula, `S/benchmark.py:127-203` (`accepted_length`, `acceptance_per_position`, `acceptance_ratio`; counters read from `llm.get_metrics()`, per-request deltas).
- Target-only: acceptance set to None (`guidellm.py:364-365`).
- Throughput: `output_tokens_per_second = total_output_tokens / (measure_end_time - measure_start_time)` from GuideLLM scheduler metrics (`guidellm.py:138-144`); wall time includes prefill, queueing, collection wait, generator.
- TTFT/latency/ITL/TPOT: GuideLLM medians `ttft_median_ms`, `latency_median_s`, `itl_median_ms`, `output_tps_median`, `tpot_median_ms` if present (`guidellm.py:125-137`) -> `perf_results.csv`. Speedup: `scripts/evaluate/compare_http.py` = candidate tok/s / baseline tok/s (`throughput_speedup`) and baseline/candidate median latency (`median_latency_speedup`); requires identical validation identity, guidellm version, concurrency, warmups, seed, max_model_len, max_num_seqs, runner, vllm version; marks `exploratory` unless correctness status in {reference, matched} (`compare_http.py:15-86`). **The suite's `summary.md` reports only output tok/s** (`suite.py:write_summary`); acceptance is in per-measurement `results.json`.
- Offline summary: output_tokens_per_second = tokens / sum(request_seconds); `mean_request_seconds`.
- Is generator latency netted out? **No.** Speedup is end-to-end including generator + (shared mode) merge/restore. Separate counters exist (`generator_seconds`, `merge_seconds`, `restore_seconds`, `mean_conditioning_size`, `mean_batch_size`, `mean_draft_batch_size`).

### 4.3 Offline (non-vLLM) quality metric
Training-time validation, not serving: teacher-forced TTT agreement. `generator/study.py:157-203` `validation()` runs generator on the held-out "tune" split per prompt (K=1 `last` context), forwards the HF/torch drafter with the factors and averages `full_acc_0` per category -> `score`/"agreement" (protocol string "singleton prompt-conditioned TTT; zero feedback; tuning split"). Replay scores `replay_scores/draft_acceptance_rate` (`study.py:~548-568`). `target_verifier.py` (`FrozenTarget`) is for **online training/feedback rollouts** (full-vocab verification with target lm_head, hidden states extracted from a vLLM extractor server), not part of the eval harness. `scripts/benchmark.py` is the upstream **training-throughput** benchmark (unrelated to serving despite name).

## 6. EAGLE-3-specific assumptions and DFlash port analysis

### 6.1 Hard-coded EAGLE-3 assumptions
- `spec.method == "eagle3"` check (`controller.py:67`); `method:"eagle3"` in all launch configs (`server.py` speculative dict; `benchmark.py:517`; kind strings `eagle3_base`, `static_lora`, `generator`, `endpoint.py`, `processes.py`).
- Patch target class is `vllm/v1/spec_decode/eagle.py::EagleProposer` (inherits vLLM's base proposer). Hooks live in that subclass only (patch lines 56-105).
- Single draft decoder layer: `AdapterMerger` (`controller.py:143`), `NativeDraftLoRA` (`multilora.py:460`, `layers[0]`), `attach_ranges` (`ranges.py:601`). Module names assume Llama/Qwen3-style vLLM layout: `draft.model.layers[i].self_attn.{qkv_proj,o_proj}`, `mlp.gate_up_proj/down_proj`.
- Checks `norm_before_residual`, `norm_before_fc`, `fc_norm`, `norm_output`, `eagle_aux_hidden_state_layer_ids` (EAGLE-3 config fields; `controller.py:130-135`); `parallel_drafting`, `disable_padded_drafter_batch` spec fields (`:103,109`).
- Proposer API: `propose(target_positions=, target_hidden_states=, common_attn_metadata=, num_rejected_tokens_gpu=, target_token_ids=, num_speculative_tokens=)` passed as **kwargs** (`patch:76-84`); `dummy_run(num_tokens=...)`, `on_requests_finished(finished_req_ids)`; per-request `input_batch.req_ids`, `requests[name].num_prompt_tokens` from the runner (`controller.py:520-543`).
- Drafting model: EAGLE-3 = autoregressive, 3 sequential draft steps over a **single causal layer**; prompt-only conditioning because the draft KV of the prompt is created at draft prefill after merge ("Full prefill is mandatory: otherwise draft KV may already contain base V", `controller.py:307`).
- Conditioning/hidden-state assumptions: aux layers `[2,18,33]`, input_dim 12288 (or 5 x 4096), `layer_ids[:-1]`.
- Scheduling restrictions: V1 runner, eager, bf16, no chunked prefill, no prefix cache, sync scheduling, TP/PP/DP=1, <= 8 seqs (`controller.py:65-103`).

### 6.2 vLLM DFlash support
- Local vLLM: not installed -> UNVERIFIED for everything below. The repo README (line 49) says DFlash models trained via Speculators "can run seamlessly in vLLM as of vLLM PR #38300", and `src/speculators/convert/dflash/converter.py` / `docs/user_guide/algorithms/dflash.md` exist (algorithms dflash, dflash2, dspark). Whether the pinned **0.31.0** contains the DFlash proposer (and its class name/location, e.g. a `dflash.py` proposer next to `eagle.py`, `method: dflash`) is UNVERIFIED; first action on the remote box: `pip show vllm; python -c "import vllm.v1.spec_decode as m; print(m.__path__)"; ls vllm/v1/spec_decode; grep -n dflash -ri vllm/config/speculative.py`.
- Nothing in the fork's serving or benchmark code mentions DFlash (`grep -ri dflash src/speculators/generator src/speculators/benchmark scripts` = no hits outside convert/models).

### 6.3 What must change to serve a DFlash drafter with generated LoRA
1. **New/extended patch** for the DFlash proposer class (whatever vLLM calls it); the current hooks on `EagleProposer` would not fire if DFlash subclasses the base proposer directly. Need a `vllm-<ver>-dflash-generator.patch` + manifest SHAs for the matching vLLM version (the whole patch machinery in `patch.py` is generic over manifest but `VLLM_VERSION` constant and the anchors are 0.31.0-specific). If 0.31.0 lacks DFlash, the vLLM version changes and **all** anchors/SHAs and the V1-runner assumption must be redone (UNVERIFIED which runners DFlash supports).
2. `validate_runtime`: replace `method == "eagle3"` with dflash; replace EAGLE-3 norm-flag checks with DFlash config checks (`dflash_config.target_layer_ids`, `mask_token_id`, `block_size`; see `convert/dflash/converter.py:86-150`); `spec.method`, `parallel_drafting`, spec-token count = block_size-1 (or block_size with `sample_from_anchor`, `dflash.md`) instead of 3.
3. **Multiple draft layers**: DFlash drafters stack several layers (converter example aux ids `[2,10,18,26,34]`; draft layer count UNVERIFIED for the target checkpoint). `AdapterMerger`/`NativeDraftLoRA` hard-assert `len(layers)==1` and `layers[0]` paths; need per-layer module names (`model.layers.{i}.self_attn...`), per-layer factors from the generator (generator heads must output per-layer A/B; bundle `shapes` per layer), and extended `expected` module sets.
4. **Non-causal block drafting with context from target states**: DFlash feeds fused target hidden states (projected context) through the draft layers as context K/V plus mask-token queries (one forward per block). LoRA on k_proj/v_proj would alter the cached context K/V for all prompt/decode positions; the "adapter fixed for the request, merge before draft prefill" invariant remains necessary but where context KV is (re)computed in the DFlash proposer (every step vs cached) is UNVERIFIED and decides whether per-request mixing of adapters in one batch is possible (per-request path also needs the punica kernels to wrap whatever linear modules DFlash layers use, and map tokens for *every* forward - DFlash has one forward per block instead of k sequential steps, which simplifies `map_forward` but the query layout (block of mask tokens + context tokens) differs from EAGLE's).
5. `fc` fusion layer (DFlash fuses `len(target_layer_ids)*hidden -> hidden`; EAGLE-3 `fc` is similar) is untouched by LoRA in the current design; if the generator also adapts it, new module support is needed (not in `ADAPTER_MODULES`).
6. Hidden-state conditioning input: reuse `target_hidden_states` from `propose()` (UNVERIFIED that DFlash's proposer receives the same kwargs/shape; if the proposer pre-fuses features through `fc`, the generator could consume either raw aux states or fused features). Layer ids come from `bundle.json["layer_ids"]` and are written to `hf_config.eagle_aux_hidden_state_layer_ids`; DFlash config key is `dflash_config.target_layer_ids` (UNVERIFIED which key vLLM reads) - must be set to the bundle's ids.
7. Benchmarks: `ARMS`, `kind` strings, `--spec-tokens` default 3, `speculative_tokens` default 3 (`B/config.py:107`), `deepspec.py` converter are EAGLE-3-specific. Acceptance counters: DFlash proposes a block at once, so `num_draft_tokens`/per-position metrics semantic (`accepted_tokens_per_pos` length = block size) differ: `acceptance_length = 1 + accepted/drafts` still valid.

### 6.4 What is reusable as is
- Bundle format/export/verification (`bundle.py`) if shapes extended per layer; `read_bundle`, sha256 checks.
- Patch installer (`patch.py`, `apply_vllm_generator_patch.py`) and manifest approach; HTTP middleware / worker extension / `/speculators/status`; `FixedBatchScheduler`; request-id lifecycle; profiling ranges.

- vLLM `create_lora_manager` multi-LoRA route (`multilora.py`) is reusable if the DFlash draft layers use LoRA-wrappable vLLM linear modules.
